# Контекст проекта для агента

## 1. Название проекта

Telegram-бот для оптимизации продуктовой корзины с доставкой.

---

# 2. Краткое описание

Пользователь один раз настраивает:

- список продуктовых магазинов;
- адрес доставки;
- максимальное количество доставок (`max_deliveries`).

После этого пользователь отправляет список продуктов в свободной форме, например:

```text
бананы 3 кг
яблоки 1 кг
творог
молоко 2 литра
```

Система должна:

1. распознать список продуктов;
2. нормализовать товары и количество;
3. найти подходящие товары в выбранных магазинах;
4. получить актуальные цены и наличие для адреса пользователя;
5. определить стоимость и условия доставки;
6. построить допустимые варианты корзины;
7. распределить товары между магазинами с учётом `max_deliveries`;
8. найти вариант с минимальной итоговой стоимостью;
9. показать пользователю понятный результат.

Пользователь **не посещает магазины лично**. Все варианты предполагают доставку.

---

# 3. Главная пользовательская ценность

Пользователь не должен самостоятельно:

- искать один и тот же товар в нескольких магазинах;
- сравнивать цены;
- пересчитывать упаковки;
- учитывать минимальные суммы заказа;
- сравнивать стоимость доставки;
- распределять продукты между магазинами.

Он пишет обычный список покупок и получает оптимальный вариант.

---

# 4. Основной пользовательский сценарий

## Первичная настройка

Пользователь:

1. запускает Telegram-бота;
2. указывает адрес доставки;
3. выбирает магазины;
4. задаёт максимальное количество доставок.

Пример:

```text
Магазины:
- ВкусВилл
- Перекрёсток
- Ашан

Максимум доставок:
2
```

Настройки сохраняются и используются для следующих запросов.

---

# 5. Основной сценарий использования

Пользователь пишет:

```text
бананы 3 кг, яблоки 1 кг, творог, молоко 2 литра
```

Система преобразует это в структурированный список:

```json
[
  {
    "name": "бананы",
    "quantity": 3,
    "unit": "kg"
  },
  {
    "name": "яблоки",
    "quantity": 1,
    "unit": "kg"
  },
  {
    "name": "творог",
    "quantity": 1,
    "unit": "package"
  },
  {
    "name": "молоко",
    "quantity": 2,
    "unit": "l"
  }
]
```

Далее система ищет варианты по выбранным магазинам и считает оптимальную комбинацию.

---

# 6. Ключевое продуктовое решение

`max_deliveries` — это **постоянная настройка пользователя**, а не режим, который пользователь выбирает при каждом запросе.

Например:

```text
max_deliveries = 2
```

означает:

> Система может разбить корзину максимум на две доставки.

При каждом новом списке система автоматически рассматривает все допустимые варианты с одной или двумя доставками.

---

# 7. Что оптимизируем

Целевая функция:

```text
минимизировать:

стоимость товаров
+ стоимость доставки
+ обязательные сервисные сборы
+ другие обязательные сборы
```

при ограничении:

```text
number_of_deliveries <= user.max_deliveries
```

Также должны выполняться ограничения конкретных магазинов:

```text
minimum_order
availability
delivery_available
```

# 8. Пример расчёта

Пользователь допускает максимум две доставки.

## Вариант A

Перекрёсток:

```text

доставка: 149 ₽
итого: 1869 ₽
```

Одна доставка.

## Вариант B


# 9. Что должен видеть пользователь

Основной результат должен быть понятным, а не техническим.

Пример:

```text
Лучший вариант — 1420 ₽

2 доставки

Ашан — 1100 ₽

- яблоки
- молоко
```

Пользователь должен иметь возможность посмотреть подробный состав корзины.

# 14. База данных

Используется PostgreSQL.

Причина практическая:

- PostgreSQL уже поднят на существующем сервере;
- для проекта можно создать отдельную БД;
- нет необходимости поднимать отдельный MySQL.

Приложение должно использовать собственную database/schema и отдельные credentials.

Не смешивать таблицы проекта с таблицами другого приложения.

# 15. Архитектурный подход

Для MVP использовать:

```text
MODULAR MONOLITH
```

Не микросервисы.

Причины:

- всего 3–4 магазина;
- небольшой объём инфраструктуры;

- проще тестирование;

- меньше operational overhead.

При этом границы модулей должны быть чёткими, чтобы позже отдельные части можно было вынести в сервисы.

# 17. Главный архитектурный контракт

Самая важная абстракция проекта:

```text
StoreAdapter
```

Каждый магазин имеет собственную реализацию, но остальная система работает с унифицированными моделями.

Пример интерфейса:

```python
class StoreAdapter:
    async def resolve_location(self, address):
        ...

    async def search(self, query, location):
        ...

    async def get_delivery_quote(self, basket, location):
        ...
```

Интерфейс может уточняться после исследования магазинов.

Но бизнес-логика не должна зависеть от внутреннего API конкретного магазина.

---

# 18. Реализации StoreAdapter

Ориентировочно:

```text

    ├── VkusvillAdapter

    ├── AuchanAdapter
    └── OtherStoreAdapter
```

Добавление нового магазина должно требовать в основном новой реализации adapter + mapping, а не изменения Optimizer.

# 24. Product Matching

Это один из ключевых компонентов.

Система должна определить, соответствует ли найденный товар запросу пользователя.

Пример:

```text
запрос: творог
```

Допустимые результаты:

```text
Творог 5% 180 г
Творог 9% 200 г
```

Нежелательные:

```text
Творожный сырок
Творожный десерт
```

Matching должен учитывать:

- название;
- категорию;
- бренд, если указан;
- жирность;
- размер;
- дополнительные характеристики;
- релевантность результата.

На первом этапе можно использовать:

```text
поиск магазина
+
правила
+
ranking
+
LLM при сложных случаях
```

Не делать LLM единственным источником истины.

# 25. Расчёт количества упаковок

Пример:

Пользователь запросил:

```text
молоко 2 л
```

Магазин продаёт:

```text
930 мл
```

Нужно купить:

```text
ceil(2000 / 930) = 3 упаковки
```

Стоимость:

```text
3 * package_price
```

Для весовых товаров использовать цену за единицу веса, если магазин поддерживает такой формат.

# 30. Потенциальная будущая настройка

После MVP можно добавить:

```text

```

Пример:

```text

```

Тогда система не предлагает вторую доставку ради экономии 50 ₽.

Это отражает пользовательскую "цену неудобства".

Не обязательно реализовывать в первом MVP.

# 31. Redis

Redis использовать только для:

- cache поиска;
- временных данных;
- TTL cache цен;
- возможно session state Telegram.

Пример cache key:

```text
store:perekrestok:location:{id}:search:молоко
```

PostgreSQL остаётся основной БД.

Запросы к магазинам выполнять параллельно:

# 35. Главные риски проекта

## 35.1 Данные магазинов

Главный риск.

Возможные проблемы:

- нет официального API;
- внутренний API нестабилен;
- требуется авторизация;
- цены зависят от адреса;
- ассортимент зависит от склада;
- rate limiting;
- CAPTCHA;
- anti-bot;
- delivery quote доступен только поздно в checkout.

Поэтому исследование магазинов идёт **до основной разработки**.

---

## 35.2 Product Matching

Один пользовательский термин может соответствовать множеству SKU.

Пример:

```text
творог
```

может означать десятки товаров.

Нужно избегать сравнения очевидно несопоставимых товаров.

---

## 35.3 Размер упаковки

Цена упаковки сама по себе недостаточна.

Нужно учитывать фактическое количество, которое необходимо купить.

---

## 35.4 Условия доставки

Математически дешёвые товары могут перестать быть выгодными после:

- delivery fee;
- minimum order;
- service fee.

Поэтому оптимизировать нужно итоговый order total.

```text
простота
```

# 41. Критерий успеха MVP

MVP успешен технически, если пользователь может выполнить:

```text
один раз:
настроить адрес
выбрать магазины
задать max_deliveries

далее:
написать список продуктов
↓
получить корректное сравнение
↓
увидеть оптимальную комбинацию доставок
↓
понять, какие товары из какого магазина предлагается заказать
```

Без ручного сравнения цен пользователем и без необходимости настраивать параметры при каждом запросе.
