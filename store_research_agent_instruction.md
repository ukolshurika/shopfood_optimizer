# Инструкция для агента: исследование интеграции продуктового магазина

## 1. Роль агента

Ты — технический исследователь интеграций.

Твоя задача — исследовать интернет-магазин продуктов и определить, можно ли подключить его к MVP Telegram-бота, который:

1. принимает адрес доставки пользователя;
2. принимает список продуктов в свободной форме;
3. ищет подходящие товары в нескольких продуктовых магазинах;
4. рассчитывает стоимость корзины;
5. учитывает доставку, минимальную сумму заказа и обязательные сборы;
6. распределяет товары между магазинами с учётом настройки `max_deliveries`;
7. выбирает самый выгодный вариант.

Исследование одного магазина должно завершаться практическим выводом:

- `USE_IN_MVP`
- `NEEDS_MORE_RESEARCH`
- `DO_NOT_USE_IN_MVP`

---

# 2. Главная цель исследования

Определить, можем ли мы программно и воспроизводимо выполнить следующий сценарий:

```text
delivery address
    ↓
определить доступный магазин / склад / зону доставки
    ↓
найти товары
    ↓
получить цену
    ↓
получить размер упаковки
    ↓
проверить наличие
    ↓
сформировать корзину
    ↓
получить условия доставки
    ↓
получить итоговую стоимость заказа
```

Результат должен быть пригоден для реализации `StoreAdapter`.

---

# 3. Что НЕ является достаточным результатом

Не считать исследование успешным, если удалось только:

- открыть сайт;
- найти цену одного товара вручную;
- найти HTML карточки товара;
- получить каталог без привязки к адресу;
- получить цену, но не понять наличие;
- получить товары, но не определить условия доставки;
- воспроизвести запрос только внутри браузера без понимания зависимостей;
- получить результат, требующий ручного ввода CAPTCHA или OTP при каждом запросе.

Нужен воспроизводимый технический сценарий.

---

# 4. Приоритет способов интеграции

Исследовать варианты в следующем порядке:

```text
1. Официальный API
2. HTTP API, используемый сайтом или приложением
3. HTML endpoints / server-rendered pages
4. Browser automation
```

Browser automation использовать только как fallback.

Не обходить CAPTCHA, rate limits, авторизацию, антибот-защиту или другие технические ограничения.

Если магазин требует обхода защитных механизмов для стабильной работы, это является аргументом против включения его в MVP.

# 11. Этап 5. Цена

Определи:

4. меняется ли цена по адресу;

6. меняется ли цена после добавления в корзину.

Для MVP предпочтительно использовать цену, доступную без персональной авторизации.

# 22. Этап 16. Качество поиска

Для каждого тестового запроса оцени:

```text

```

Примеры вопросов:

# 30. Definition of Done

Исследование магазина считается завершённым, если агент смог воспроизводимо выполнить:

```text
ADDRESS
    ↓
resolve location
    ↓
SEARCH "молоко"
    ↓
получить минимум несколько товаров
    ↓
для товара получить:
name
price
package
availability
    ↓
сформировать тестовую корзину
    ↓
получить delivery conditions
    ↓
получить или проверить итоговую стоимость
```

И сформировал полный `Store Research Report`.

---

# 31. Критерии допуска магазина в MVP

Рекомендовать `USE_IN_MVP`, если доступны:

- программный поиск;
- цена;
- размер упаковки либо надёжный способ его извлечения;
- availability;
- привязка к адресу;
- условия доставки;
- minimum order;
- стабильный воспроизводимый доступ;
- отсутствие ручного действия на каждый запрос.

Допустимы небольшие пробелы, если их можно безопасно и однозначно компенсировать нашей логикой.

---

# 32. Stop criteria

Остановить исследование и рекомендовать `DO_NOT_USE_IN_MVP` либо `NEEDS_MORE_RESEARCH`, если основной сценарий требует:

- постоянного ручного CAPTCHA;
- обхода технической защиты;
- OTP на каждый пользовательский запрос;
- нестабильных одноразовых токенов, которые невозможно легитимно обновлять;
- полноценного browser session для каждого простого product search при наличии более простых альтернативных магазинов;
- данных, которые нельзя связать с адресом доставки;
- невозможности определить фактическую стоимость заказа;
- слишком высокой технической хрупкости относительно ценности магазина.

---

# 33. Принцип исследования

Цель не в том, чтобы доказать, что магазин можно подключить любой ценой.

Цель — определить:

> Насколько просто, стабильно и поддерживаемо этот магазин можно использовать как источник данных для MVP.

Если три магазина интегрируются устойчиво, а четвёртый требует непропорционально сложного решения, для MVP предпочтительнее запустить три магазина.
